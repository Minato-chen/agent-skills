# Notion project summary

Keep technical records and interview preparation together on a single Notion project page. Summarize completed or ongoing work honestly; do not implement code or perform unrelated changes to make the narrative stronger. Use the user's preferred language, defaulting to Chinese when appropriate.

## Establish identity and evidence

1. Identify the project, requested reporting scope, and current milestone. Inspect relevant repository changes, issues, PRs, releases, test results, and discussion when available. Distinguish observed facts, user-provided statements, and unknowns; do not invent commands, outcomes, impact, or collaboration.
2. Find the existing page by stable identity, prioritizing repository/product URL or a known page ID over title similarity. If multiple candidates remain, prepare the update and clarify the target before writing. If no page exists, create one only when the intended parent location is clear and creation is authorized by the request.
3. Read the current page before updating. Preserve useful history and unrelated content. Use available Notion capabilities for actual access; the skill itself provides no credentials or permissions. If access or destination is unavailable, prepare a ready-to-paste update and state precisely what was not saved.
4. Verify current external status before labeling work submitted, approved, merged, released, or deployed. Link sources and include relevant dates. A passing local test or submitted PR is not evidence of a released change.

## Maintain one project record

Use these sections for an initial full summary; adapt headings to an existing page rather than creating duplicate structures:

1. **项目概况** — repository/product link, goal, personal role, current state, and milestone dates.
2. **问题与实现** — original problem, evidence, approach, personal contribution, key decisions, and tradeoffs.
3. **验证与结果** — checks actually run and outcomes, manual evidence, PR/release links, limitations, and measurable impact only when supported.
4. **团队协作** — actual participants or roles, feedback, response, resulting changes, unresolved differences, and follow-up. Link discussion; describe solo work honestly.
5. **面试表达** — a concise spoken account of background, responsibility, challenge, decisions, results, and collaboration; likely follow-up questions with evidence-based answers. Tailor to the target role when known. Mark unfinished work and unverified impact explicitly.
6. **后续事项** — review, maintenance, blockers, and next steps.

For later updates, revise only affected sections and append a brief dated milestone note. Preserve enough history to explain status transitions. Avoid copying the full technical account into the interview section; select the decisions and contributions that support a clear spoken story. Do not inflate a small fix into a major feature or force a full six-section rewrite for every milestone.

## Verify the update

Check that links, dates, attribution, completion states, and test claims agree across sections. After writing, read back the changed content to confirm it reached the intended page without losing prior material. Report the page link and what was updated. If writing or verification fails, state the partial result accurately and retain the prepared text.
