# Finish code work

Scale the workflow to the task. Apply relevant rules lightly for small changes and expand investigation for complex or risky behavior. Do not force new plan files, architecture records, or approval steps for routine work. Apply relevant checks internally and report only decision-relevant findings. For small edits, use the narrowest faithful check; do not copy the entire project, run every test, or prolong investigation unless output behavior or risk requires it.

## Scope and baseline

1. Determine whether the user requests explanation, review, planning, implementation, or release. Discussion alone produces a proposal, not edits. Once implementation is authorized, complete the requested outcome without repeatedly seeking confirmation for routine steps.
2. Read repository instructions, relevant code, requirements, and existing tests. Define acceptance criteria from the user's actual request; do not substitute an easier milestone for the requested result. Identify the authoritative delivery directory, which is normally the requested checkout or platform-managed worktree. Keep repository-specific commands and conventions in its AGENTS.md or equivalent.
3. Inspect the initial branch, tracked changes, untracked files, and relevant tool versions. Preserve all pre-existing work. Before editing or copying changes back, recheck affected files against the version last read; if another actor has changed them, reread and integrate the new content instead of overwriting it from a stale snapshot. Do not reset, stash, revert, delete, or overwrite user changes merely to obtain a clean tree.
4. Change only files necessary for the task. Avoid unrelated refactors, whole-repository formatting, dependency upgrades, lockfile churn, and generated-file changes. Include dependency, lockfile, or generated-file updates when required for the requested behavior or repository conventions; explain their necessity and validate them. Do not add debug entry points, test buttons, fake data, or temporary instrumentation to production source for convenience.

## Code design and style

1. Follow repository instructions and established naming, layout, formatting, error handling, and framework conventions. When conventions are absent, prefer official documentation and examples for the installed version. Verify uncertain APIs from installed code or official references rather than inventing them from memory. Adapt teaching examples with necessary error handling, boundary checks, and resource cleanup.
2. Search for existing implementations and working examples before adding code. Prefer an existing owner of the behavior, standard library, platform API, or suitable installed dependency over duplicate logic or unnecessary dependencies.
3. Give functions and modules clear responsibilities. Separate presentation, domain logic, and persistence where their responsibilities or reasons for change justify it. Keep interfaces small, data flow explicit, and dependencies understandable; avoid circular dependencies, deep nesting, hidden mutable state, and unnecessary order dependencies.
4. Modularize to support concrete responsibilities, reuse, or change needs. Keep simple behavior direct; do not introduce speculative frameworks, rigid layers, excessive tiny files, or abstractions merely to appear modular. Default to the existing structure. A new abstraction must solve a current, specific responsibility, duplication, or change problem; a generic claim of improved maintainability is insufficient. Do not impose universal line-count limits or unfamiliar architecture on an existing project.
5. Place new files by their role in the project's existing structure and complete imports, registration, exports, and callers. Use meaningful names in the project's vocabulary. Explain constraints and non-obvious decisions in comments, not obvious operations; leave no commented-out legacy code. Validate inputs at real trust boundaries and handle demonstrated failure modes. Within the codebase, rely on explicit contracts; avoid redundant null checks, speculative fallbacks, and silent defaults that hide invalid states.
6. Apply style improvements within the necessary change. Do not expand a bug fix into cleanup or refactoring. Remove code orphaned by this change only after confirming it is unused, including dynamic registrations or external consumers where relevant. Every new file, abstraction, and dependency must have a concrete purpose.

## Minimal fixes and regression control

1. Establish the trigger, actual behavior, and expected behavior. Reproduce where feasible; if reproduction is unavailable, identify the evidence and uncertainty instead of asserting a confirmed cause.
2. Trace relevant calls, data flow, state, and recent changes. Compare with working code and version-appropriate references. State a specific root-cause hypothesis supported by evidence before changing behavior. Proceed when evidence is sufficient for a testable fix; continue investigation only when the remaining uncertainty could change the implementation or its safety. Do not require exhaustive certainty for a small, well-understood bug.
3. Test one main hypothesis at a time in the isolated environment. If it fails, reassess the evidence and remove only your failed experimental changes before trying a different explanation; do not pile speculative patches on top. Repeated failures require revisiting assumptions and coupling, not automatically declaring the architecture wrong or forcing a fixed attempt limit.
4. Fix the root cause at the responsible boundary with the smallest necessary behavioral impact, not simply the fewest changed lines. Preserve unrelated behavior, public interfaces, persisted formats, and defaults. If compatibility or a wider change is necessary, explain the evidence and impact.
5. Do not mask a bug by swallowing errors, forcing defaults, disabling features, relaxing assertions, or weakening tests unless that behavior is explicitly required as an appropriate fallback. Keep refactoring separate unless it is necessary for a correct fix. Record unrelated issues without fixing them unless they directly block the requested result.
6. Check the original trigger, normal behavior, and directly affected boundaries or neighboring paths. When feasible, confirm the same reproducer fails before the fix and passes afterward in isolation. Automated regression coverage is valuable when proportionate; manual or targeted checks are acceptable when better suited, with limits stated. Test observable behavior rather than incidental implementation details.

For requested behavior-preserving refactors, establish the relevant observable behavior and checks before restructuring, then compare using the same checks afterward in isolation. Describe any intended behavior change separately; do not label an unverified rewrite behavior-preserving.

## Isolate testing

1. Before running checks, identify where they write files and whether they start processes or modify persistent state. Create a unique task-owned temporary directory outside the working repository. Put ad hoc test scripts, fixtures, logs, screenshots, caches, coverage, and build outputs there; redirect tool outputs when supported.
2. If a tool requires repository-local outputs or temporary source changes, run it in an isolated copy or worktree outside the working repository. Include the current intended changes and needed pre-existing work, not merely HEAD. Before testing, confirm that relevant source, configuration, assets, and test files match the current intended deliverable, including required untracked files and pre-existing edits. Use a scoped file comparison or content hashes where useful; never assume a fresh worktree includes uncommitted changes. Refresh the isolated copy and rerun affected checks after later code changes. Keep dependencies and configuration suitable for the check, and do not copy secrets unnecessarily. Report any material difference between the isolated environment and the actual project. If implementation occurs in a disposable copy, review and transfer only intended source changes and durable tests to the delivery directory; do not copy back caches, instrumentation, fixtures, or the entire tree. Recheck destination files for concurrent edits, confirm transferred content matches the tested version, and rerun affected checks if integration changed it. When delivery is blocked, preserve a reviewable patch and report it as prepared but not applied; never delete the only copy of the intended changes during cleanup.
3. Choose the smallest isolated environment that can faithfully exercise the requested behavior. Include necessary scenes, assets, and imports for engine projects, but avoid blindly duplicating large unrelated datasets or dependencies. Do not share writable caches, build directories, fixtures, or mutable service state with the original project. Resolve symlinks and inspect tool output/configuration paths before running checks; reuse shared resources only when access is effectively read-only and cannot write back. Before the first potentially stateful check, verify where resolved file paths, environment/configuration, subprocesses, and service connections can write, using available read-only inspection or a safe dry run. A separate directory alone is not evidence of isolation. Redirect or replace shared writable destinations with task-owned resources; check actual output locations afterward and reassess the boundary when configuration changes. If reliable isolation is unavailable, complete safe checks and report the remaining verification as blocked instead of silently running it in the original project. Do not claim isolation or regression freedom beyond the boundaries and behavior actually checked.
4. Keep durable regression tests in the project's established test directory when they meaningfully protect changed behavior. Treat these as intentional deliverables, not disposable verification files. Follow existing embedded-test conventions only when appropriate and clearly include such changes in the final diff. Run tests with generated artifacts and mutable state isolated.
5. Use disposable test storage and services. Do not run destructive checks against real user data, production resources, or shared state. Do not edit ignore rules merely to hide test pollution or install dependencies globally for convenience.
6. Choose checks proportionate to the change. For UI work, inspect rendering and affected interactions; for engine projects, check project loading and relevant scenes; for libraries, exercise affected behavior and meaningful edge cases. Map each important acceptance criterion to a check and its observed result. Verify the affected behavior and meaningful edge cases, not merely startup or compilation; for save/load fixes, exercise saving, reloading, and restored state. Mark each criterion passed, failed, or unverified; avoid a formal table for trivial tasks. Do not add tests that only mirror the implementation.
7. Separate new regressions, baseline failures, and environment limitations. Fix task-related failures and rerun affected checks; do not weaken tests or change unrelated code to manufacture a passing result. Never claim checks passed when they were not run. Evidence must apply to the current intended version: rerun affected checks after relevant changes, test/environment changes, or failures. Reuse still-valid results when no relevant change occurred; do not mechanically repeat the entire suite before every reply.

## Cleanup and completion

1. Track task-owned resources proportionately. For one short-lived check, a scoped temporary directory and automatic cleanup are sufficient; do not create a manifest merely for ceremony. For multiple directories, long-lived processes, services, worktrees, or resumable work, keep a small cleanup manifest outside the repository as resources are created. Retain enough ownership information to identify them after interruption without recording secrets. Use try/finally or shell traps for normal exits, but do not assume these run after forced termination. On success, failure, or early termination, stop only task-owned processes and remove only confirmed task-owned temporary artifacts. On resuming an interrupted task, check for leftover owned artifacts before creating more.
2. Preserve requested evidence as a named deliverable before deleting temporary outputs. Remove isolated copies or worktrees through the appropriate tool. Avoid broad deletion, repository-wide clean commands, or resetting tracked files as a cleanup shortcut.
3. Compare final status against the initial baseline. Inspect the full diff, untracked and ignored outputs, generated files, dependency changes, and debug remnants. Confirm each change serves the request, that a maintainer can identify the entry point and main data flow, and that new boundaries or abstractions have a concrete purpose. The final tree should contain intended deliverables and the user's original work. Treat cleanup as a separate completion criterion. Attempt safe recovery from cleanup failures and verify that registered resources were removed or intentionally retained as deliverables. If permissions or environment constraints prevent cleanup, report implementation and cleanup states separately, identify the exact remaining artifact or resource and the blocker, and give a safe removal step when possible. Do not claim full completion or successful cleanup while task-owned disposable artifacts remain. When a cleanup manifest exists, remove it last after confirming cleanup; retain it when needed for recovery.
4. Report what changed, why, observed verification, material limitations, and actual completion state. Keep small-task reports brief. If blocked, preserve useful progress and name the unresolved requirement.

## Open source and external actions

Read contribution rules and relevant maintainer discussion for upstream work. Prepare a reproducible issue/PR explanation and cite real discussion when relevant. Distinguish local changes, submitted PRs, approved PRs, merged changes, and releases. Drafting a reply is different from sending it; commits, pushes, messages, merges, and deployment follow the user's existing authorization and applicable environment rules.

Do not make Notion updates part of every code task. When project documentation or interview preparation is requested or already authorized, hand actual evidence to notion-project-summary; lack of Notion access does not invalidate completed code work.
