# Presentation workflow

Use the user's existing deck, template, language, and established decisions as constraints. First determine whether the request is for discussion, creation, or revision. A request for advice or a plan produces a reviewable proposal only. Once the user asks to execute or accepts the proposal, complete the edit without asking again.

## Plan before building

For a new deck, agree on the audience, purpose, central question, available time, and overall page map before making slides. Show what each page will cover and how sections connect. Within a section, make the reasoning progressive where the material has a dependency; keep genuinely parallel topics parallel.

Before production, turn the page map into a concrete page blueprint: for each page give its purpose, proposed title, actual draft wording, visual or data source, and what goes in each region of the page (for example, upper left, center, right, footer). Include the intended reading or speaking order and transition to the next page. Plan an explanation before the first use of a term the audience may not know. Do not rely on a later page to define a term needed now.

For revision, inspect the target page and enough surrounding context to understand its role. State the intended message and propose exact changes to wording, visual, placement, and speaking order. Preserve the whole-deck logic while editing only the requested pages or objects. Treat user comments on an earlier response as concrete revision requirements.

## Present clearly

Prefer one main message per page. Make the visual and words support that message, with language understandable on first viewing without artificially casual wording. Distinguish what a diagram illustrates from what measured data establish; label an example or schematic when it could be mistaken for an observed result. Keep definitions, units, legends, assumptions, and sources close enough to the claim they clarify. Verify source-backed or time-sensitive claims when they matter to the slide.

Default to the user's current top-title/body-below template: black text, a common title size across pages, a common body size across pages, and smaller notes only where needed. Use Chinese 黑体, Japanese 明朝, and English Times New Roman unless the existing template or the user specifies otherwise. Maintain alignment and comfortable slide-size readability; do not shrink text merely to fit more content. Prefer editable slide objects for simple diagrams that may be revised. Keep a reusable SVG source for complex vector diagrams, and use data plots from their actual analysis source.

For a bilingual deck, first establish the languages' roles and layout for that request. Keep parallel text equivalent in meaning and keep terms, numbers, symbols, units, and citations aligned. Use each language's font rule. If two languages crowd a page, restructure or split the content while preserving the approved argument.

## Produce and verify

When creating or editing, save a new version using the established base name plus `V` and the next number only; do not add feature descriptions to the version name. Preserve the prior approved version. Render the result at presentation size and inspect reading order, line breaks, figure labels, legibility, and consistency. For a scoped revision, compare with the source and verify that unrelated pages did not change. Keep only necessary deliverables and source assets; avoid stray test outputs.
